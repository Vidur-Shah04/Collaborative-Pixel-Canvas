# Ordered operations foundation

This branch adds a fixed-owner protocol foundation. Each coordinator draw receives an operation ID (or uses the client's supplied ID), carries the current tile epoch, and is sent to the owner in the coordinator's durable SQLite registry. The registry seeds a tile from the deterministic Stage 3A mapping on first use and survives coordinator container recreation in `coordinator_data`. The shard commits pixels, a per-tile sequence, and a draw event in one SQLite transaction. Repeating an operation ID with the same payload returns the stored result without another write or sequence increment; reusing it for different content returns 409. New operations apply in tile sequence order. A tile snapshot reads its pixels and last sequence in one SQLite transaction. `/tiles/{tile_id}/operations?after=N` reads durable history after a sequence boundary.

Clear shares this per-tile history. The coordinator records its stable operation ID, initiating session, participants, coordinates, and phase. Shards first commit the owner-scoped pixel deletions. Only after every shard has committed does the coordinator enter `finalizing`; shards append one Clear event for each affected tile at that tile's next sequence. The event payload includes the parent Clear ID, user/session ID, and coordinates. A no-op Clear has a coordinator history row but changes no tile and needs no tile event. The coordinator reports completion only after every participant finalizes. If a commit or finalization fails, its coordinator phase remains pending; startup recovery retries it and blocks draws and migration until done. This protocol is recoverable, not atomic. Some shard history can be finalized before another participant becomes available, but migration/replay through the coordinator is withheld until global completion.

The per-tile sequence is sufficient for reconstructing the canvas because pixel operations on different tiles cannot affect the same coordinate. This does not create a total order for cross-tile timelapse. Snapshot restore installs the state and sequence from a tile checkpoint; operation import then replays later draws and Clear events. Clear replay removes only coordinates that still carry the initiating user, and later draw events restore any subsequently written pixels. Clear operations completed before ordered Clear history was deployed cannot be retroactively assigned an exact sequence; the schema migration preserves them as legacy-complete records without claiming exact replay.

An active shard can persist a checkpoint using `POST /tiles/{tile_id}/snapshots`. It stores the snapshot ID, ownership epoch, last tile sequence, and pixel rows in the shard's SQLite file. `POST /tiles/{tile_id}/snapshots/{snapshot_id}/restore` atomically restores those pixels and replays all later contiguous per-tile operations. The checkpoint and log are in the same shard volume; this protects against process restarts, not loss of the volume. Restoring never rewrites operation IDs or lowers the current ownership epoch or sequence.

History now includes typed Undo records. Successful Undo checks the current owner and expected color before restoring the pixel value saved when the user's draw committed; a mismatch is a sequenced no-effect record, preserving a newer user's overwrite. Replay applies an Undo only when the expected pixel still matches. The coordinator stores per-session action order and attempt IDs, and permits no more than ten attempts per session.

`GET /hash` verifies final visible state with SHA-256. It serializes a fixed canvas/version header followed by occupied pixels sorted by row-major tile index, local y, and local x; each line contains tile index, local coordinates, and uppercase `#RRGGBB`. Ownership metadata is excluded, so shard placement and current owner do not affect the hash. This hash compares a recovered canvas to a reference state; it does not create a reference chronology.

A correct whole-canvas timelapse still requires a total order across tiles. The current independent tile sequences cannot determine whether an update in tile A happened before or after one in tile B. A future coordinator journal could assign a durable global sequence after each operation's shard commit and finalize Clear only after every participant completes; it would need a pending-intent/reconciliation protocol for crashes between the coordinator and shard commits. Until then, do not sort by timestamp or tile ID and present that as chronological. Final-state replay and hash verification remain well-defined without this global journal.

Browser synchronization uses these same per-tile cursors. A shard's `GET /tiles/positions` returns durable ownership rows, including a fenced source until the coordinator records the destination as owner. The coordinator filters by its ownership registry. It combines those cursors with authoritative pixels for `GET /state` and the initial WebSocket `state` message while holding its canvas lock; it registers the socket and sends the snapshot before allowing a later mutation to broadcast. Draw messages carry one tile position, and a Clear message carries one position for each changed tile. The browser ignores events at or below its cursor and applies only the next sequence. A gap, malformed cursor, or backwards epoch closes the socket and fetches a fresh snapshot through reconnect. Thus updates during snapshot acquisition are either in the snapshot and its cursors or delivered afterward. This relies on one coordinator serializing every mutation and does not order events across different tiles. If shard state is incomplete, the snapshot fails and the browser stays disabled until retry succeeds.

The initial assignment remains the Stage 3A modulo mapping. Tile ownership can move between configured shards: the coordinator records a pending transfer, copies a snapshot and bounded log pages while the source continues accepting draws, then briefly pauses that tile, fences the source, copies the final writes, activates the destination at the next epoch, and updates its ownership record. Draws remain available during the copy phase. Requests for that tile return 503 during the final fence and cutover, or while recovery is pending after a failure. Repeating the same transfer request resumes it. The admin route requires `ADMIN_TOKEN` in the coordinator environment and the matching `X-Admin-Token` request header.

Example, after setting `ADMIN_TOKEN` for the coordinator and starting Compose:

```sh
curl -X POST -H 'X-Admin-Token: YOUR_TOKEN' 'http://localhost:8000/admin/tiles/0/0/transfer?destination=shard-2'
```

This is live copy with a **brief fenced cutover**, not a zero-pause transfer. A stopped coordinator leaves the durable transfer row in place. On restart, the coordinator retries pending transfers in the background; it also retries while a shard is unavailable and finishes when that shard returns. If failure occurs before fencing, source draws can continue; after fencing, the tile remains unavailable until recovery finishes. Do not change active `SHARD_IDS` while data matters. Clear uses the protocol above and is **recoverable but not atomic** across independent SQLite databases: a failure during commit can temporarily expose a partial result until recovery. Migration is blocked during incomplete Clear history finalization. Snapshot responses are migration checkpoints, not a catalog of long-term historical snapshots. There is no cross-coordinator coordination or authentication on shard-internal endpoints beyond the private Compose network.

Remaining verification work: run the browser and real-container suites in an environment with Playwright and Docker available, and exercise longer histories and prolonged outages. The current `/hash` endpoint verifies visible final state; historical full-canvas replay and chronological timelapse remain unsupported. A correct timelapse needs a durable coordinator commit journal with pending-intent recovery across shard commits, including an explicit policy for multi-tile Clear. Do not infer cross-tile chronology from timestamps or tile IDs. Dynamically adding a shard is also unsupported: changing active `SHARD_IDS` changes the initial modulo ownership mapping, so a safe membership/rebalancing protocol is required first. An epoch change must continue to fence the old shard before the new one can commit.
